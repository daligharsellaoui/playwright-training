Module 0

Initiation : comprendre Playwright

Durée ~45 min de lecturePrérequis bases de JavaScript, async/await

Qu'est-ce que Playwright ?

Playwright est un framework de tests end-to-end (E2E) open source maintenu par Microsoft. Il pilote de vrais navigateurs (Chromium, Firefox, WebKit) avec une seule API, et fournit son propre test runner, @playwright/test : parallélisme, retries, rapports, traces.

Point fortCe que ça change pour toi
Auto-waitingAvant chaque action, Playwright attend que l'élément soit visible, stable, activé et prêt à recevoir le clic. Pas de sleep.
Web-first assertionsexpect(locator) réessaie jusqu'à ce que la condition soit vraie, ou jusqu'au timeout.
IsolationChaque test reçoit un browser context neuf, comme un profil incognito : pas de cookies partagés entre tests.
OutillageCodegen, UI mode, Inspector, Trace Viewer, rapport HTML.
RéseauInterception, mock, et tests d'API sans navigateur.

Les trois niveaux : Browser, Context, Page

Browser (un process Chromium / Firefox / WebKit, partagé par un worker) ├── BrowserContext (session isolée : cookies, localStorage, permissions) │ ├── Page (un onglet) │ └── Page └── BrowserContext (le test suivant : tout neuf) └── Page

Lancer un navigateur coûte cher, alors qu'un context se crée en quelques millisecondes. Playwright réutilise donc le navigateur et crée un context par test. C'est ce qui rend les tests à la fois rapides et indépendants.

Anatomie d'un test

import { test, expect } from '@playwright/test'

test.describe('Login', () => {                        // groupe (optionnel)
  test.beforeEach(async ({ page }) => {               // hook
    await page.goto('/')
  })

  test('shows an error for a locked user', async ({ page }) => {
    await page.getByLabel('Username').fill('locked_user')   // action (auto-wait)
    await page.getByLabel('Password').fill('secret_sauce')
    await page.getByRole('button', { name: 'Login' }).click()

    await expect(page.getByRole('alert')).toContainText('locked out') // assertion (retry)
  })
})
  • { page } est une fixture : Playwright la crée avant le test et la nettoie après. Autres fixtures intégrées : context, browser, request, browserName…
  • Chaque action et chaque expect(locator) renvoie une Promise : toujours await. Un await oublié est le bug n°1 du débutant.

Locator : une recette, pas un élément

page.getByRole('button', { name: 'Login' }) ne cherche rien au moment où tu l'écris. C'est une description, évaluée à chaque utilisation. Tu peux donc créer un locator avant que l'élément existe, et le réutiliser après un re-render.

Un locator est strict : si une action vise un locator qui matche 2 éléments, Playwright lève une strict mode violation au lieu de cliquer au hasard.

Auto-waiting et web-first assertions

// ❌ Lit la valeur UNE fois, sans attendre : fragile
expect(await page.getByTestId('cart-badge').textContent()).toBe('2')

// ✅ Réessaie jusqu'à 5 s : robuste
await expect(page.getByTestId('cart-badge')).toHaveText('2')

// ❌ Jamais : attente arbitraire, lente ET fragile
await page.waitForTimeout(2000)

Du CSS fragile aux locators utilisateur

Ciblage dynamique d'un produit

Les 6 produits ont tous un bouton « Add to cart ». page.getByRole('button', { name: 'Add to cart' }).click() lève donc une strict mode violation. Il faut d'abord filtrer la carte, puis chercher dans la carte.

test('add a specific product to the cart', async ({ page }) => {
  // (login comme ci-dessus)
  const card = page.getByTestId('product-card').filter({ hasText: 'Bolt T-Shirt' })
  await card.getByRole('button', { name: 'Add to cart' }).click()
  await expect(card.getByRole('button', { name: 'Remove' })).toBeVisible()
})

Factorise le filtre dans une fonction réutilisable :

import type { Page } from '@playwright/test'

export const productCard = (page: Page, name: string) =>
  page.getByTestId('product-card')
    .filter({ has: page.getByRole('heading', { name, exact: true }) })
Pourquoi has + exact plutôt que hasText ?hasText: 'T-Shirt' matche « Bolt T-Shirt » et « Red T-Shirt ». Filtrer sur le titre exact ne laisse aucune ambiguïté.

Pick locator

En UI mode, clique sur l'icône cible « Pick locator », puis survole un élément de la page : Playwright te propose le meilleur locator. Utile quand tu hésites.

À toi
  • Vérifie qu'il y a 6 cartes : await expect(page.getByTestId('product-card')).toHaveCount(6).
  • Lis le prix de « Fleece Jacket » via productCard(), et vérifie $49.99.
  • Trouve le titre « Products » avec getByRole('heading').
  • Trouve le select de tri avec getByLabel('Sort by').

Page Object Model

Durée ~2 hNotions classes, encapsulation, composants, données de test

Le POM regroupe les locators et les actions d'une page dans une classe. Si l'UI change, tu corriges un seul endroit, et les tests se lisent comme un scénario métier.

Une première page : LoginPage

e2e/pages/LoginPage.ts 
import type { Locator, Page } from '@playwright/test'

export class LoginPage {
  readonly username: Locator
  readonly password: Locator
  readonly submit: Locator
  readonly error: Locator

  constructor(private readonly page: Page) {
    this.username = page.getByLabel('Username')
    this.password = page.getByLabel('Password')
    this.submit = page.getByRole('button', { name: 'Login' })
    this.error = page.getByRole('alert')
  }

  async goto() {
    await this.page.goto('/')
  }

  async login(username: string, password: string) {
    await this.username.fill(username)
    await this.password.fill(password)
    await this.submit.click()
  }
}

Une page avec des méthodes paramétrées : InventoryPage

e2e/pages/InventoryPage.ts 
import type { Locator, Page } from '@playwright/test'
import { Header } from './components/Header'

export class InventoryPage {
  readonly header: Header
  readonly cards: Locator

  constructor(private readonly page: Page) {
    this.header = new Header(page)
    this.cards = page.getByTestId('product-card')
  }

  async goto() {
    await this.page.goto('/inventory.html')
  }

  productCard(name: string) {
    return this.cards.filter({ has: this.page.getByRole('heading', { name, exact: true }) })
  }

  async addToCart(name: string) {
    await this.productCard(name).getByRole('button', { name: 'Add to cart' }).click()
  }

  // TODO: removeFromCart(name), sortBy(value), prices()
}

Le test réécrit

test('buy two products', async ({ page }) => {
  const login = new LoginPage(page)
  const inventory = new InventoryPage(page)
  const cart = new CartPage(page)
  const checkout = new CheckoutPage(page)

  await login.goto()
  await login.login(USERS.standard.username, USERS.standard.password)
  await inventory.addToCart('Backpack')
  await inventory.addToCart('Onesie')
  await expect(inventory.header.cartBadge).toHaveText('2')
  await inventory.header.openCart()
  await cart.checkout()
  await checkout.fillShipping({ firstName: 'Ada', lastName: 'Lovelace', postalCode: '75001' })
  await checkout.placeOrder()
  await expect(checkout.confirmDialog).toContainText('$37.98')
  await checkout.confirm()
  await expect(page.getByRole('heading', { name: 'Thank you for your order!' })).toBeVisible()
})
Règles de bon POM
  • Les méthodes expriment une intention (addToCart('Backpack')), pas un geste (clickButton3()).
  • Pas d'expect dans les POM pour commencer : ils exposent des locators, et les tests vérifient.
  • Pas de if ni de logique de test dans les POM.
À toi
  • Termine InventoryPage, puis écris CartPage (items, total, remove, clear({ accept }), checkout) et CheckoutPage.
  • Migre tous les tests des modules 2 à 4.
  • Checkpoint : grep -r "getBy" tests/ ne renvoie (presque) rien.
Module 6

StorageState & fixtures

Durée ~2 hNotions projet setup, dependencies, storageState, test.extend

Le problème

Chaque test se reconnecte par l'UI : c'est lent, et ça teste le login 50 fois. La solution est de se connecter une fois, de sauvegarder l'état du navigateur (cookies + localStorage) dans un fichier JSON, puis de démarrer chaque test avec cet état.

Le fichier de setup

e2e/tests/auth.setup.ts 
import { test as setup, expect } from '@playwright/test'
import { USERS } from '../test-data/users'

const authFile = '.auth/user.json'

setup('authenticate', async ({ page }) => {
  await page.goto('/')
  await page.getByLabel('Username').fill(USERS.standard.username)
  await page.getByLabel('Password').fill(USERS.standard.password)
  await page.getByRole('button', { name: 'Login' }).click()
  await expect(page).toHaveURL(/inventory/)   // attendre que le cookie soit posé
  await page.context().storageState({ path: authFile })
})

Brancher le setup dans la config

projects: [
  { name: 'setup', testMatch: /.*\.setup\.ts/ },
  {
    name: 'chromium',
    use: { ...devices['Desktop Chrome'], storageState: '.auth/user.json' },
    dependencies: ['setup'],          // setup tourne toujours avant
  },
],

Ajoute .auth/ au .gitignore : ce fichier contient une session valide. Ouvre-le et repère le cookie sid.

Exclure les tests de login

// en haut de login.spec.ts : ces tests partent d'un navigateur vierge
test.use({ storageState: { cookies: [], origins: [] } })

Variante rapide : login par l'API

setup('authenticate via API', async ({ request }) => {
  const response = await request.post('/api/login', { data: USERS.standard })
  expect(response.ok()).toBeTruthy()
  await request.storageState({ path: authFile })    // récupère le cookie sid
})

On passe de ~1 s à ~50 ms. Le login UI reste couvert par login.spec.ts.

Custom fixtures : injecter les pages

e2e/fixtures/index.ts 
import { test as base } from '@playwright/test'
import { InventoryPage } from '../pages/InventoryPage'
import { CartPage } from '../pages/CartPage'

type Fixtures = {
  inventoryPage: InventoryPage
  cartPage: CartPage
}

export const test = base.extend<Fixtures>({
  inventoryPage: async ({ page }, use) => {
    const inventoryPage = new InventoryPage(page)
    await inventoryPage.goto()                // setup
    await use(inventoryPage)                  // le test s'exécute ici
    // teardown éventuel après use()
  },
  cartPage: async ({ page }, use) => {
    await use(new CartPage(page))
  },
})

export { expect } from '@playwright/test'
import { test, expect } from '../fixtures'

test('add to cart updates the badge', async ({ inventoryPage }) => {
  await inventoryPage.addToCart('Backpack')
  await expect(inventoryPage.header.cartBadge).toHaveText('1')
})

Une fixture n'est créée que si un test la demande. Les fixtures peuvent dépendre les unes des autres (cartPage peut demander inventoryPage).

À toi
  • Fixture cartWithItems : remplis le panier sans passer par l'UI, avec page.addInitScript(() => localStorage.setItem('cart', '[1,5]')).
  • Fixture lockedUserPage.
  • Question : pourquoi la session est-elle partagée entre tests, mais pas le panier ? (Indice : chaque test reçoit son propre context, initialisé avec une copie du fichier.)

Module 8

Interception & mock API

Durée ~2 hNotions page.route, fulfill, fetch, waitForRequest, fixture request

Partie A — Intercepter le réseau du navigateur

Remplacer complètement une réponse

test('shows mocked products', async ({ page }) => {
  await page.route('**/api/products', (route) =>       // AVANT le goto
    route.fulfill({ json: [
      { id: 98, name: 'Mocked Mug', price: 0.01, description: 'From the mock' },
      { id: 99, name: 'Mocked Cap', price: 1.5, description: 'From the mock' },
    ] })
  )
  await page.goto('/inventory.html')
  await expect(page.getByTestId('product-card')).toHaveCount(2)
  await expect(page.getByText('$0.01')).toBeVisible()
})

Modifier la vraie réponse

await page.route('**/api/products', async (route) => {
  const response = await route.fetch()                 // appel au vrai serveur
  const products = await response.json()
  products[0].name = 'Mocked Backpack'
  await route.fulfill({ response, json: products })
})

Simuler une erreur et une latence

// Erreur serveur
await page.route('**/api/products', (route) =>
  route.fulfill({ status: 500, json: { error: 'Database down' } }))
await page.goto('/inventory.html')
await expect(page.getByRole('alert')).toHaveText('Could not load products: Database down')

// Latence : vérifier l'état de chargement
await page.route('**/api/products', async (route) => {
  await new Promise((r) => setTimeout(r, 2000))
  await route.continue()
})
await page.goto('/inventory.html')
await expect(page.getByRole('status')).toHaveText('Loading products…')
await expect(page.getByRole('status')).toBeHidden()

Espionner une requête sans la mocker

const orderRequest = page.waitForRequest(
  (req) => req.url().endsWith('/api/orders') && req.method() === 'POST')
await page.getByRole('dialog').getByRole('button', { name: 'Confirm' }).click()
const body = (await orderRequest).postDataJSON()
expect(body).toEqual({
  items: [1, 5],
  shipping: { firstName: 'Ada', lastName: 'Lovelace', postalCode: '75001' },
})
Ordre importantCrée la promesse waitForRequest avant le clic, et fais l'await après. Sinon, la requête peut partir avant que tu l'écoutes.

Partie B — Tester l'API directement

Un fichier de tests API pur

e2e/tests/api/products.spec.ts 
import { test, expect } from '@playwright/test'

test.use({ storageState: { cookies: [], origins: [] } })   // partir sans session

test('health is public', async ({ request }) => {
  const res = await request.get('/api/health')
  expect(res.status()).toBe(200)
  expect(await res.json()).toEqual({ status: 'ok' })
})

test('products require a session', async ({ request }) => {
  expect((await request.get('/api/products')).status()).toBe(401)
})

test('logged-in user gets 6 products', async ({ request }) => {
  await request.post('/api/login', { data: { username: 'standard_user', password: 'secret_sauce' } })
  const res = await request.get('/api/products')          // le cookie est conservé
  expect(res.ok()).toBeTruthy()
  const products = await res.json()
  expect(products).toHaveLength(6)
  expect(products[0]).toEqual(expect.objectContaining({ id: expect.any(Number), name: expect.any(String) }))
})
À toi
  • Liste vide [] : aucune carte. L'utilisateur voit une page blanche : note-le comme un bug UX.
  • POST /api/orders mocké en 400 { error: 'Payment declined' } : le message s'affiche sur le checkout.
  • API : /api/products/999 → 404, commande sans postalCode → 400, commande valide → 201 avec total correct.
  • Hybride : crée l'état par l'API, puis vérifie-le par l'UI.

Le header s'adapte au mobile

Sous 640 px, la nav est cachée derrière le bouton « Open menu », donc openCart() échoue sur le projet mobile. On corrige le POM, pas les tests :

async openCart() {
  const burger = this.page.getByRole('button', { name: 'Open menu' })
  if (await burger.isVisible()) await burger.click()
  await this.cartLink.click()
}
Exception à la règle « pas de if dans les POM »Ici, le if décrit le comportement de l'UI (responsive), pas une logique de test. C'est justement le genre de détail que le POM doit cacher.

Tests spécifiques et tags

test('burger toggles the menu', { tag: '@mobile' }, async ({ page, isMobile }) => {
  test.skip(!isMobile, 'Burger only exists on small screens')
  await page.goto('/inventory.html')
  const burger = page.getByRole('button', { name: 'Open menu' })
  await expect(burger).toHaveAttribute('aria-expanded', 'false')
  await burger.click()
  await expect(page.getByRole('button', { name: 'Close menu' })).toHaveAttribute('aria-expanded', 'true')
})

Intégration GitHub Actions

Durée ~1 hNotions workflow, artefacts, config CI, sharding

Publier le repo

Crée un repo GitHub personnel, puis pousse tout playwright-training/ (app + tests dans le même repo).

Adapter la config au CI

workers: process.env.CI ? 2 : undefined,
reporter: process.env.CI ? [['html'], ['github']] : 'html',   // 'github' annote les PR

Le workflow

.github/workflows/playwright.yml (à la racine du repo) 
name: Playwright
on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 20
    defaults:
      run:
        working-directory: e2e
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx playwright install --with-deps     # navigateurs + libs système
      - run: npx playwright test                    # webServer démarre demo-shop
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}                     # même (surtout) si rouge
        with:
          name: playwright-report
          path: e2e/playwright-report/              # relatif à la racine du repo
          retention-days: 14

Exploiter un run rouge

  1. Casse un test, puis commit et push.
  2. GitHub → Actions → le run → Artifacts → télécharge playwright-report.
  3. Dézippe-le, lance npx playwright show-report chemin/du/dossier, puis ouvre la trace.
À toi (bonus)
  • Sharding : strategy.matrix.shard: [1/2, 2/2] + --shard=${{ matrix.shard }}, reporter blob, puis un job merge-reports.
  • GitLab CI, plus proche de ce que tu utilises au travail : un .gitlab-ci.yml avec l'image mcr.microsoft.com/playwright:v<ta-version>-noble et artifacts: when: always.
  • Ajoute le badge du workflow dans le README.

Les 7 péchés du débutant

  1. Oublier un await.
  2. waitForTimeout au lieu d'une assertion.
  3. expect(await x.textContent()) au lieu de expect(x).toHaveText().
  4. Sélecteurs CSS ou XPath couplés à l'implémentation.
  5. Tests qui dépendent les uns des autres (ordre, données partagées).
  6. Se connecter par l'UI dans chaque test.
  7. Déclarer un page.route ou un waitForRequest après l'action qui déclenche la requête.
